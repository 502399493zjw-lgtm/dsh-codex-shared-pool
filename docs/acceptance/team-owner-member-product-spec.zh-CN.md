# Team Owner / 成员产品规格

**状态：** Draft v0.2

**日期：** 2026-08-22

**适用范围：** DSH Codex Shared Pool Team 的成员、邀请码、所有权、用量投影、个人账号共享边界与生命周期

**不包含：** 页面视觉稿、生产实现计划、账号容量策略细节、基于长期闲置的自动休眠策略

## 1. 目标

本规格将 Team 权限模型收敛为：

- 每个有效 Team 必须且只能有 1 位 `Team Owner`；
- Team 中可以有 0 位或多位普通`成员`；
- 不再存在 `Admin`，也不再提供通用的“修改成员角色”能力；
- 只有当前 Team Owner 可以生成邀请码、管理成员、暂停 Team、转让所有权和解散 Team；
- 普通成员可以使用 Team、通过现有 Codex 账号管理区管理自己的共享配置，以及主动退出 Team。

本规格的首要目标是让用户始终能回答以下问题：

1. 谁拥有这个 Team？
2. 谁当前可以访问这个 Team？
3. 新成员如何获得访问权？
4. 移出、退出、断开设备和解散分别会影响什么？
5. Team Owner 如何安全地转让或终止 Team？
6. Team 产生了多少可验证的共享 Token 与 API 等价预估费用？

## 2. 产品原则

### 2.1 权限保持最小化

- Team 级管理能力只属于当前 Team Owner。
- 普通成员看不到无权使用的管理入口，不展示禁用按钮或空的邀请码页面。
- 所有权限都必须由服务端重新校验，不能只依赖前端隐藏。

### 2.2 身份、设备与容量分离

- 成员身份表示某人是否属于 Team。
- 设备凭据表示某一台 Host 是否能代表该成员访问 Team。
- 提供容量表示某个成员是否允许 Team 使用其 Codex 容量。
- 断开设备、退出 Team 和停止提供容量是三种不同操作，不得互相替代。

### 2.3 高风险操作必须可解释

- 暂停是可恢复的 Team 运行控制。
- 移出和主动退出会终止一名成员的访问权。
- 解散会终止整个 Team，且不可恢复。
- 每个确认界面必须描述操作对象、作用范围、可恢复性和凭据后果。

### 2.4 Browser 不持久化原始凭据

- Browser 的常规 Team 投影只包含最小、无秘密的数据。
- Team API Key 和 Codex 授权永不下发 Browser，其持久化由 Host 或服务端负责。
- 邀请码是唯一明文例外：Browser 可在生成结果、当前 Owner 主动发起的再次查看结果和加入输入的组件内存中短暂接收。新码或再次查看结果仅用于展示和用户主动复制；粘贴的码提交给 Host 建立短时预览会话后，Browser 立即清空输入，由 Host 接管后续加入。
- 含邀请码的 Host 响应必须返回 `Cache-Control: no-store`，Browser 请求使用禁用缓存模式；邀请码不得进入 URL、Browser 持久化存储、日志或遥测，只有用户主动点击复制时才可写入系统剪贴板。
- 完整邀请码不得常驻邀请列表或其他普通 Team 投影。当前 Owner 可以对尚未使用、未到期且未撤销的邀请码显式执行`查看邀请码`；每次关闭查看界面后 Browser 立即清除明文，再次查看必须重新向 Host 请求并重新鉴权。

## 3. 核心术语与不变量

### 3.1 Team Owner

- 创建或初始化 Team 的成员自动成为首位 Team Owner。
- 一个处于`运行中`或`已暂停`状态的 Team 必须始终恰好有一位活跃 Team Owner。
- Team Owner 不能被移出、不能直接降级，也不能直接退出 Team。
- Team Owner 只能通过原子所有权转让变为普通成员。
- Team Owner 可以在任意成员数量下解散 Team。

### 3.2 成员

- 成员通过有效邀请码加入 Team。
- 新加入者一律成为普通成员，邀请码不能指定更高角色。
- 成员可以主动退出，但不能邀请、移出他人、转让所有权、暂停或解散 Team。
- 被移出或退出后再次加入，会创建新的成员记录，不恢复旧成员身份和旧容量授权。

### 3.3 成员显示名称

- 显示名称先去除首尾 Unicode 空白并执行 NFKC 规范化；规范化后的值必须为 1–120 个 Unicode scalar values，不按 UTF-8 字节或 UTF-16 code units 计数。
- 原始值和规范化值均不得包含 Unicode 控制字符、`Default_Ignorable_Code_Point` 或 `Bidi_Control`；`NFKC_Casefold` 比较值不得为空。
- 同一 Team 内的活跃成员名称必须按 locale-independent Unicode `NFKC_Casefold` 比较值保持唯一；界面保存和展示通过校验后的规范化显示值，不使用 locale-specific 大小写规则。
- 本规格固定使用 Unicode 15.1.0 数据执行上述校验和比较；升级 Unicode 数据版本必须通过显式数据迁移和唯一性复检，不能跟随运行环境静默变化。
- 服务端必须同时持久化显示值和规范化比较值，并以数据库部分唯一约束保证`同一 team_id 下 status = active 的比较值`唯一；不得依赖数据库默认 collation。
- 已移除成员不占用名称；重新加入可以再次使用该名称。
- 显示名称不是账号身份验证，不绑定邮箱、OpenAI 账号或自然人。

### 3.4 唯一 Owner 不变量

任何服务端写操作均不得产生以下状态：

- `active` 或 `paused` Team 中有 0 位活跃 Team Owner；
- `active` 或 `paused` Team 中有 2 位或更多活跃 Team Owner；
- 已解散 Team 中仍存在可认证的 Team Owner；
- 普通成员通过旧 API 或直接请求获得 Team 管理权限。

若在 `active` 或 `paused` Team 中读取到零个或多个 Owner，应视为数据完整性错误，阻止所有管理变更并要求服务端修复，不能作为普通空状态展示。`dissolved` Team 则必须没有任何活跃成员或可认证 Owner。

## 4. 范围

### 4.1 本规格包含

- Team Owner 和成员两角色模型；
- 成员列表；
- 一次性邀请码的生成、预览、使用、过期和撤销；
- 邀请加入和不确定结果恢复；
- 移出成员；
- 成员主动退出；
- Team Owner 转让；
- Team 暂停与恢复；
- Team 解散；
- Team 共享汇总、个人 Team 用量、预估费用、Token 和数据完整状态的最小投影；
- 当前成员自己的共享开关与状态；
- 本机连接异常的清理语义；
- 权限、安全、并发和审计要求。

### 4.2 本规格不包含

- Admin、自定义角色或自定义权限；
- 多 Owner；
- 邮箱、通讯录或指定身份邀请；
- 邀请邮件发送、重发、延期或编辑；
- Team 改名、头像、简介、部门或品牌设置；
- 成员头像、邮箱、在线状态或“最后活跃时间”；
- 成员暂停、恢复或审批加入；
- 席位数、成员上限或计费；
- Provider 实际账单、订阅实付、账户余额、费用分摊、成员账单、人民币换算或 USD 之外的币种；
- 向 Browser 展示逐请求用量，或展示输入、缓存输入和输出 Token 拆分；
- Browser 中的完整设备与 Team Key 管理；
- Browser 中创建 Team；Team 继续由现有部署或 bootstrap 流程初始化；
- 容量提供页面的具体限制字段和视觉结构。
- 基于闲置时长自动暂停、归档或解散 Team；本版只提供 Owner 手动暂停、恢复和解散。

## 6. Team 生命周期

### 6.1 用户可见状态

| 状态 | 含义 | 可恢复 |
| --- | --- | ---: |
| `active` / 运行中 | 可以加入并承接新的共享请求 | — |
| `paused` / 已暂停 | 进入低资源休眠：阻止加入、新请求和后台主动容量刷新，保留成员和数据 | 是 |
| `dissolved` / 已解散 | Team 永久终止 | 否 |

### 6.2 状态转换

```text
初始化
  ↓
运行中 ⇄ 已暂停
  │         │
  └────┬────┘
       ↓
    已解散
```

- `正在确认解散结果`只是当前 Host 的操作恢复状态，不是 Team 的持久化生命周期状态。
- 解散事务将 Team 从 `active` 或 `paused` 原子转为 `dissolved`，同时终止全部成员；不能提交一个已终止成员但 Team 尚未解散的中间状态。
- `dissolved` 是终态，不能通过恢复、重新连接或新邀请码重新激活。
- 解散请求必须支持幂等确认；客户端超时不能被当作失败或成功。

### 6.3 状态写入规则

- 只允许`初始化 → active`、`active → paused`、`paused → active`和`active | paused → dissolved`。
- Team 必须持久化从初始化开始单调递增的`lifecycleRevision`，并随无秘密状态投影返回；每次成功的暂停、恢复或解散转换恰好递增一次，任何流程都不能回退或复用旧 revision。
- 暂停、恢复和解散请求必须携带随机幂等操作 ID 与调用者看到的`expectedLifecycleRevision`。服务端在 Team 锁内同时比较当前状态和 revision；任一不匹配均返回 `409`并要求刷新，不能让`active → paused → active`后的陈旧请求再次命中`active`。
- 完全相同的操作 ID 与绑定可幂等返回原结果；新操作对已处于目标状态的 Team 只有在 expected revision 等于当前 revision 时才返回无变更成功，不递增 revision、不重复写审计事件。
- `dissolved`不接受任何暂停、恢复或普通管理写入；陈旧恢复请求必须返回终态，绝不能重新激活 Team。
- 解散的幂等确认只能走绑定原操作的恢复协议；被撤销的旧 Owner Key 只能获得 §17.4 的粗粒度终态，不能重新执行解散。

### 6.4 闲置时间与自动状态转换

- 本版不存在“超过 N 天未使用”后自动暂停、归档或解散的状态转换；仅仅经过时间不能改变 Team 生命周期状态、成员身份、邀请码、设备凭据或容量配置。
- 每个新的 Team 网关请求完成最终服务端准入时，必须以服务端时钟写入一条无请求内容的使用事件，事件的`startedAt`即权威`admittedAt`。若路由层曾创建临时 Lease、但最终容量预留或使用事件写入失败，该 Lease 必须结算释放且不构成一次成功准入。请求进入最终准入后，其上游结果成功、失败或取消均不改变原`admittedAt`。
- 服务端应基于上述权威事件持久化仅供 Host 运维和未来闲置策略使用的可空单调摘要`lastTeamRequestAt = max(admittedAt)`。摘要可以异步汇总，不能要求每个并发请求更新 Team 生命周期行，也不能作为当前版本改变 Team 状态的依据。
- Team 初始化但从未成功准入请求时，`lastTeamRequestAt`为空；未来若计算闲置时长，以`createdAt`作为新 Team 的起点。旧 Team 的历史不完整时不得把空值解释为“从未使用”。
- 设置页浏览、邀请码预览、Key 认证、健康检查、后台容量刷新和失败的请求准入都不得更新`lastTeamRequestAt`，避免保活流量或后台任务掩盖真实闲置。
- `lastTeamRequestAt`不是成员在线状态或成员“最后活跃时间”，不包含请求内容，也不在本版 Browser 投影中展示。
- 未来若引入自动休眠，只能进入可恢复的`paused`状态，并复用 §6.3 的 Team 锁、`lifecycleRevision`、审计和并发规则。长期闲置不能自动进入不可恢复的`dissolved`；解散仍需当前 Team Owner 明确确认。

## 7. 成员列表

### 7.1 展示内容

成员列表不显示头像。每行只展示：

- 显示名称；
- 角色：`Team Owner` 或`成员`；
- 当前用户标记：`我`；
- Team Owner 可见的单个 `···` 操作菜单。

示例：

```text
Edison Zhong                         Team Owner · 我
Alice                                成员              ···
Bob                                  成员              ···
```

### 7.2 排序与计数

- Team Owner 固定排第一。
- 其他成员按加入时间从早到晚排列。
- 默认列表只包含 `active` 成员。
- 页面中的成员数必须与实际展示的活跃成员行数一致。
- 已移除成员只保留在服务端审计中，不出现在普通成员列表。

### 7.3 操作入口

- Team Owner 自己的行不显示移出操作。
- 普通成员查看列表时不显示任何成员管理菜单。
- Team Owner 查看普通成员时，行内菜单只包含`移出 Team`。
- `转让 Team Owner`属于 Team 级所有权操作，只从 Team 管理菜单进入，不在每一行重复展示。
- Browser 只接收`可接任 / 不可接任`结果，不接收该成员的设备数量、Key 或其他凭据详情。
- 不存在“升为管理员”“降为成员”或任意角色选择器。

## 8. 邀请码

### 8.1 产品语义

邀请码是一次性的 Bearer 访问凭据：谁持有并最先成功使用，谁就能加入。

因此：

- 邀请码不绑定邮箱、成员名称或自然人；
- 邀请说明会展示给持码加入者，不是私密的内部备注；
- 产品文案不得声称“已邀请某个确定的人”；
- Owner 应被提醒只通过可信渠道发送邀请码。

### 8.2 可见性

- 只有当前 Team Owner 能看到邀请码管理入口和有效邀请码元数据，并能通过显式操作再次查看有效邀请码的完整值。
- 普通成员既不能生成邀请码，也看不到待使用邀请码的说明、数量和到期时间。
- 未加入用户持有某一个完整邀请码时，只能预览该邀请码对应的 Team 名称、邀请说明、到期时间和当前运行状态；这不授予邀请码列表或其他 Team 数据的读取权。
- 权限必须在 Browser 投影和服务端 API 两层同时限制。

### 8.3 生成邀请码

仅运行中的 Team Owner 可以生成邀请码。

输入字段：

- 邀请说明：必填；去除首尾 Unicode 空白并执行 NFKC 后为 1–120 个 Unicode scalar values，原始值和规范化值均不得包含控制字符、`Default_Ignorable_Code_Point`或`Bidi_Control`；持码者可以看到，不能填写秘密；
- 有效期：1 天、7 天或 30 天；默认 7 天。

创建时间取服务端时钟，`expiresAt = createdAt + N × 24 小时`，不按自然日或本地夏令时计算；仅当`serverNow < expiresAt`时有效，等于到期时间即视为过期。

成功后：

- 展示完整邀请码；
- 提供`复制邀请码`操作；
- 明确提示“关闭后仍可从邀请码列表再次查看”；
- 服务端同时保存用于接受时恒定时间比对的安全摘要，以及仅供当前 Owner 再次查看的认证加密密文；
- 不自动发送消息、邮件或通知。

创建提示：

> 邀请码等同于一次性访问凭据，请只发送给目标成员。邀请说明会展示给持码者，但不会限制谁可以使用。

### 8.4 邀请列表

主列表只展示尚未使用、未到期且未撤销的邀请码：

- 邀请说明；
- 创建时间；
- 到期时间；
- 对`revealable = true`的新邀请码展示`查看邀请码`操作；升级前摘要-only 邀请改为不可查看说明；
- 撤销操作。

完整邀请码不得直接写在列表行、页面 HTML 初始数据或普通列表响应中。当前 Owner 对`revealable = true`的记录点击`查看邀请码`后，Host 通过独立的非缓存请求重新鉴权并只在弹窗内返回该条仍有效的邀请码；关闭弹窗立即清除 Browser 明文，之后仍可再次点击查看。`revealable = false`的升级前摘要-only 邀请只显示`旧邀请码无法查看，请撤销后重新生成`和撤销操作。已使用、已过期和已撤销记录不进入主列表，只保留在服务端审计中，且不能再次查看完整值。

Team 暂停时，邀请码页顶部显示：

> Team 已暂停。以下邀请码暂时不能用于加入；恢复后，届时仍未过期的邀请码可继续使用。

暂停不新增邀请码生命周期状态；列表行使用临时说明`暂停期间不可用`，不能仍标成“可立即使用”。

空状态：

> 暂无有效邀请码。每个邀请码只能成功加入一名成员。

### 8.5 邀请码状态机

```text
生成
  ↓
有效 ──首次成功加入──→ 已使用
  ├──到期────────────→ 已过期
  ├──Owner 撤销──────→ 已撤销
  ├──转让 Owner──────→ 已撤销
  └──解散 Team───────→ 已撤销
```

规则：

- 每个邀请码只能成功创建一名成员。
- 并发使用同一邀请码时，只能有一个请求成功。
- 预览不消费邀请码。
- 已使用、已过期或已撤销的邀请码不能恢复。
- 再次查看不消费也不延期邀请码；Team 暂停期间仍允许当前 Owner 查看和撤销，但邀请码依然不能用于加入。
- Team 暂停后不能生成或使用邀请码；已有邀请码保留，且到期时间继续计算。持码者仍可预览并看到`Team 已暂停`，但加入按钮禁用且服务端提交不会消费邀请码。
- Team 恢复后，尚未到期且未撤销的邀请码可以继续使用。
- 所有权转让完成时，Team 中全部尚未使用的邀请码失效；新 Owner 需要重新生成。

### 8.6 撤销邀请码

只有当前 Team Owner 可以撤销有效邀请码。

确认文案：

> 撤销后，已经分享出去的邀请码会立即失效，不影响已经加入的成员。

按钮：`撤销邀请码`

## 9. 加入 Team

加入流程属于未连接状态下的 onboarding，不属于已加入后的 Team 设置。

### 9.1 前置条件

- 当前 Host 没有有效 Team 连接；
- 当前 Host 没有待恢复的加入操作；
- 本机凭据存储可写；
- 邀请码有效。

如果当前 Host 已连接另一个 Team，必须阻止加入，不能静默覆盖现有连接。

有效邀请码在 Team 处于`运行中`或`已暂停`时均可预览。只有 Team 处于`运行中`时才能提交加入；`已暂停`时展示状态和说明，但禁用加入按钮。

### 9.2 标准流程

1. 用户粘贴邀请码。
2. Browser 将邀请码一次性提交给 Host。Host 在请求远端预览前生成至少 128 bit 随机熵的加入操作 ID 和一份独立的至少 256 bit 恢复秘密，只把`操作 ID + 恢复秘密摘要 + 邀请码`提交给服务端。
3. 服务端返回无秘密预览和一个经过签名的 opaque `joinLocator`。locator 必须绑定`attemptId + teamId + inviteId + operationId + recoverySecretDigest + attemptExpiresAt`，有效期最长 15 分钟；它只能用于定位并认证这一加入 attempt，不授予 Team 预览、加入或其他 Team 权限。
4. 每份待用邀请码在服务端同一时刻最多有一个未过期的加入 attempt 槽。完全相同的操作 ID 与恢复摘要可幂等取回同一槽；其他操作 ID 在槽释放或到期前统一冲突，不创建新的操作记录。旧 locator 到期后永久不能接受或消费邀请码；只有邀请码仍待用、未过期且 Team 仍可预览时，服务端才可签发下一槽。
5. Host 将完整邀请码、操作 ID、恢复秘密和`joinLocator`放入最长 15 分钟的内存预览会话，并向 Browser 返回无秘密投影和本机 opaque handle；Browser 随即清空邀请码输入。关闭或取消页面时 Host 尽力释放槽并立即清除会话，15 分钟 TTL 是最终失效保障。
6. 展示 Team 名称、邀请说明、有效期和运行状态。
7. 用户输入显示名称，并显示辅助文案：`请输入 Team Owner 能识别的名称；名称不代表经过验证的身份。`
8. 明确显示：`你将以成员身份加入`。
9. 用户点击`以成员身份加入`。
10. Host 根据本机 handle 取回预览会话；locator 已过期或不足以覆盖一次正常请求窗口时，Host 必须先结束旧 attempt，并用新的操作 ID 与恢复秘密重新执行预览以建立新槽，不得用旧 locator 发起接受。
11. Host 生成一份至少 256 bit 随机熵的候选 Team API Key。
12. Host 将`操作 ID + 恢复秘密 + 候选 Key + 邀请码 + joinLocator + 规范化显示名称 + 请求摘要`写入受保护的本机待加入记录，写入成功后删除内存预览会话；这些秘密和 locator 均不下发 Browser。
13. Host 提交操作 ID、恢复秘密摘要、候选 Key、邀请码、`joinLocator`和显示名称；服务端先由 locator 只读定位 Team，再按 §17.2 锁定和复检，在同一事务中认领 attempt 槽、接受邀请码、创建普通成员、登记该 Key、持久化加入操作结果，并写入 §17.3 定义的最小加入提交标记。
14. Host 收到`accepted`后先将候选 Key 提升为正式连接并持久化结果；收到确定拒绝时持久化拒绝结果。随后按 §17.3 ACK 该操作，ACK 确认后清除恢复秘密、邀请码和其他待加入材料。

邀请码消费、成员创建、候选 Key 登记和成功操作结果必须全有或全无。候选 Key 无效、重复或无法登记时，不能留下成员，也不能把邀请码标记为已使用。只有 `joinLocator` 能安全解析到 Team、且需要冻结可变拒绝结果时，服务端才保存幂等拒绝记录；未知或畸形 token 使用统一响应、限速且不产生无界操作记录。

### 9.3 加入失败

| 场景 | 用户提示 | 是否消费邀请码 |
| --- | --- | ---: |
| 已使用、过期、撤销、所属 Team 已解散或格式错误 | 邀请码无效或已失效，请向 Team Owner 获取新的邀请码。 | 否 |
| Team 已暂停 | 该 Team 当前已暂停，暂时不能加入。请联系 Team Owner。 | 否 |
| 显示名称重复 | 这个成员名称已被使用，请换一个名称。 | 否 |
| 当前设备已连接其他 Team | 请先处理当前 Team 连接，再加入新的 Team。 | 否 |
| 本机凭据不可写 | 无法安全保存 Team 访问凭据。 | 否 |

### 9.4 结果不确定

网络超时、服务端 5xx 或响应丢失不能直接当作加入失败，因为邀请码可能已被成功消费。

此时：

- Host 保留操作 ID、独立恢复秘密、候选 Key、邀请码、`joinLocator`和完整待加入记录；
- 页面只显示`恢复加入`和`取消加入`；
- 用户不能再次提交邀请码；
- 恢复操作先用`操作 ID + 恢复秘密`查询加入结果：`accepted`时提升连接；确定的`rejected`或`canceled`时显示原因；收到统一的`unknown_or_unauthorized`结果时，Host 以完全相同的操作 ID、恢复摘要、候选 Key、邀请码、locator 和名称重试原请求，服务端若已有不同绑定则返回 `409`；
- 加入操作查询必须在候选 Key 后续被移出、退出、撤销或 Team 解散后仍能返回该次加入的原始结果和当前粗粒度终态，不能仅靠当前 Key 是否可认证推断；
- `取消加入`不是本地丢弃。Host 必须提交操作 ID、独立恢复秘密、`joinLocator`及原请求绑定；服务端由 locator 定位 Team，与邀请接受使用同一 Team 锁，并持久化互斥的取消结果；
- 若取消先线性化，服务端创建`canceled`操作 tombstone，后到的接受请求不得创建成员或消费邀请码；若接受先线性化且新成员仍为普通成员，取消执行一次补偿退出后才确认，邀请码保持已使用；
- 若接受先线性化后该成员已成为 Team Owner，取消不得破坏唯一 Owner 不变量；服务端返回`accepted_owner`，Host 必须保留并提升正式连接，提示用户先转让所有权或解散 Team；若成员已被移出、已退出或 Team 已解散，则返回原始`accepted`及当前终态，Host 可安全清除候选连接；
- `canceled`、`rejected`或`expired_no_commit`这类没有创建成员、登记 Key 或消费邀请的终态，只占用该 invite 的同一个 attempt 槽。locator 到期后，任何迟到接受都必须确定性拒绝；服务端可在`attemptExpiresAt + 24 小时网络宽限期`后回收未 ACK 的无副作用操作行，因为签名 locator 自身保留了操作 ID 与恢复摘要绑定。
- 回收后查询必须先验证 locator 签名、操作 ID 和恢复秘密，再进入与接受相同的 Team 线性化边界，确认 locator 已过期且不存在该`attemptId + operationId`的加入提交标记，才能返回权威`expired_no_commit`。加入事务一旦产生过成员、Key 或邀请消费，必须原子写入不可由普通 ACK 或结果 GC 删除的提交标记；存在标记时返回`accepted`及可用的粗终态，绝不能因为完整结果已清理而改报未提交。伪造 locator、错误秘密和不匹配操作 ID 仍返回统一的`unknown_or_unauthorized`；
- 无副作用 attempt 到期或 ACK 后，如果邀请码仍待用且未过期，其他用户可以重新预览并建立新槽；旧 locator 和旧操作 ID 永远不能复活。
- 通常只有确定终态已持久化且 §17.3 ACK 确认后，Host 才清除恢复秘密和待加入材料；唯一例外是服务端在验证签名 locator 与恢复秘密后返回上述`expired_no_commit`，它本身就是“从未产生远端副作用且旧 locator 永不可提交”的终态证明，Host 持久化该无秘密结果后可直接清理。远端不可达时可以停止自动重试，但必须保留密封的恢复记录，不能提供不安全的强制本地丢弃。

两份不同邀请码并发提交相同规范化显示名称时，只能有一份成功。失败请求不得消费邀请码，也不得留下成员或设备凭据。

## 10. 移出成员

### 10.1 权限与入口

- 只有当前 Team Owner 可以移出普通成员。
- Team Owner 不能移出自己。
- 入口位于目标成员行的 `···` 菜单。

### 10.2 服务端效果

成功移出必须作为一个受保护的成员终止操作：

- 目标成员变为已移除；
- 撤销该成员全部 Team 设备凭据；
- 目标成员提供的容量立即停止承接新请求；
- 已准入的请求允许完成并记录结果；
- 标记其 Team 贡献为已撤销；
- 外部上游凭据清理失败时进入可重试清理，不恢复成员权限；
- 写入成员移出审计事件。

### 10.3 确认文案

> 将「Alice」移出 Team？
> 该成员会立即无法访问 Team；其提供给 Team 的账号也会停止接收新请求。正在进行的请求不会被中断。此操作无法撤销。

按钮：`移出 Team`

### 10.4 被移出成员的下一次访问

- 服务端拒绝其全部旧凭据；
- 服务端必须通过 §17.4 的 Key 诊断 tombstone 返回`你已被移出 Team`终态，不得退化为无法区分的通用连接错误；
- Host 展示`清除本机连接`；
- 重新加入必须使用新邀请码，并创建新成员记录。

## 11. 成员主动退出

### 11.1 普通成员

普通成员可以主动退出 Team。

退出后：

- 成员身份变为已移除；
- 全部 Team 设备凭据撤销；
- 其提供的 Team 容量停止承接新请求；
- 已准入请求允许完成；
- 服务端结果确认后，当前 Host 删除本机 Team 连接；
- 重新加入需要新的邀请码。

确认文案：

> 退出「Design Team」？
> 退出后，你会立即无法访问 Team；你提供给 Team 的账号也会停止接收新请求。重新加入需要 Team Owner 提供新的邀请码。

按钮：`退出 Team`

### 11.2 Team Owner

Team Owner 不显示普通的`退出 Team`按钮，而是显示说明：

> Team Owner 不能直接退出。请先将 Team Owner 转让给一名成员，或者解散 Team。

Owner 只有两条合法离开路径：

1. 转让 Team Owner 后，以普通成员身份退出；
2. 永久解散 Team。

### 11.3 结果不确定

- 提交退出前，Host 必须生成随机的操作 ID 和至少 256 bit 的恢复秘密，并在本机安全保存。
- 已认证的退出请求携带操作 ID 和恢复秘密摘要；服务端在同一成员终止事务中持久化幂等结果。
- 退出事务撤销成员凭据后，Host 仍可凭`操作 ID + 恢复秘密`访问仅返回该次退出结果的专用查询端点；它不能读取 Team 数据或发起其他操作。
- 远端退出结果不确定时不得先删除本机凭据或恢复秘密；Host 必须先重试同一操作或查询最终成员状态。
- 远端明确确认成员已移除后，Host 先持久化无秘密的本机终态标记并停止使用旧连接，再显式 ACK；ACK 响应丢失时以相同操作重复 ACK，确认后才删除恢复秘密。
- 删除本机正式凭据独立重试，不阻塞 ACK。可写存储删除失败时展示`退出已完成，本机连接清理待重试`；只读来源展示手动清理说明，但两者都不能继续尝试 Team 认证。
- 记录绑定、错误响应、保留和 ACK 规则统一遵守 §17.3。

## 12. 转让 Team Owner

所有权转让采用“当前 Owner 发起、目标成员接受”的两阶段流程。转让请求不是第三种角色；完成前双方角色不变。

### 12.1 发起转让

前置条件：

- 调用者仍是当前 Team Owner；
- 目标是同一 Team 的另一名活跃普通成员；
- 目标至少有一份仍有效的 Team 设备凭据；
- Team 处于`运行中`或`已暂停`状态；
- 当前不存在另一份待处理的所有权转让请求。

转让界面只列出服务端投影为`可接任`的成员，不返回设备数量或 Key。发起后：

- 当前 Owner 仍是唯一 Owner，并继续拥有全部管理权限；
- 目标仍是普通成员；
- 尚未使用的邀请码继续有效；
- 转让请求以服务端时钟创建，`expiresAt = createdAt + 24 小时`，当`serverNow >= expiresAt`时到期；
- 当前 Owner 可以撤销，目标成员可以拒绝；
- 目标被移出、主动退出或 Team 解散时，请求自动取消。

待处理转让请求的投影只下发给当前 Owner 和指定目标；其他成员不能看到目标、状态或时间。服务端以数据库约束保证每个 Team 最多一份待处理请求。

### 12.2 目标成员确认

目标成员打开 Team 控制面时看到持久提示，直到接受、拒绝、被撤销或到期。只有指定目标可以接受或拒绝。

接受请求必须使用目标成员当前仍有效的设备凭据完成一次实时认证；这既是同意接任，也是目标仍可访问 Team 的证明。Team 暂停不阻止接受，但 Team 已解散时请求失效。

### 12.3 状态机与并发

```text
pending ──目标接受──→ accepted
   ├─────目标拒绝──→ rejected
   ├─────Owner 撤销→ revoked
   ├─────到期──────→ expired
   └─────目标退出、被移出或 Team 解散──→ canceled
```

- 五种终态互斥且不可恢复；不能先显示拒绝或到期、随后又完成转让。
- 接受、拒绝、撤销、到期处理和自动取消都必须按`Team → 转让请求 → 成员 → 设备凭据`顺序进入同一线性化边界，并在锁内重验角色、目标、状态和服务端时间。
- 并发操作中先获得 Team 线性化点并提交者获胜；后到操作返回已提交终态，不创建第二个终态或重复审计。
- 到期不是仅由前端计时；后台任务或下一次读取/写入在 Team 锁内将逾期的`pending`请求原子改为`expired`。

### 12.4 原子完成

目标接受后，服务端在同一 Team 级事务中：

- 锁定 Team、目标成员和用于接受的设备凭据，并重新验证请求、双方身份和凭据均有效；
- 目标成员从`成员`变为`Team Owner`；
- 原 Team Owner 从`Team Owner`变为`成员`；
- 任何可观察时刻都不能存在零个或两个 Owner；
- 原 Owner 立即失去邀请码、成员管理、暂停和解散权限；
- 用于接受的目标凭据保持有效，双方其他有效设备凭据不变；
- 双方各自提供的容量及归属保持不变；
- 全部尚未使用的邀请码被撤销；
- 转让请求变为已完成并写入审计事件。

若目标凭据撤销先提交，接受失败且角色不变；若接受先提交，并发撤销必须遵守最后 Owner 访问保护，不能撤销新 Owner 的最后一份服务端有效凭据。

### 12.5 文案

发起确认：

> 邀请「Alice」接任 Team Owner？
> 对方接受前，你仍是 Team Owner。对方接受后，你会变为成员，全部尚未使用的邀请码会失效。成员显示名称不代表经过验证的身份，请先通过可信渠道确认「Alice」是预期成员。

按钮：`发送转让请求`

目标成员：

> 「Edison」邀请你接任 Team Owner。
> 接受后，你将负责邀请成员、管理 Team 运行和解散 Team。

按钮：`接受并成为 Team Owner`、`拒绝`

没有可接任成员时：

> 当前没有可以接任 Team Owner 的成员。请先邀请一名成员成功连接 Team。

## 13. 暂停与恢复 Team

### 13.1 权限

- 只有当前 Team Owner 可以暂停或恢复 Team。
- 普通成员只查看状态，不能操作。

### 13.2 暂停效果

Team 暂停后：

- 阻止新的共享请求；
- 阻止新成员加入；
- 阻止生成新邀请码；
- 已生成邀请码不能使用，但继续自然到期；
- 已准入请求允许完成；
- 暂停提交后不再为该 Team 选择新的定时 Provider 容量刷新或其他 Team 专属后台轮询；暂停提交前已经发出的有限刷新可以完成，但返回结果必须保留其发起时的`observedLifecycleRevision`，只能被丢弃或保存为陈旧快照，不能伪装为当前可路由容量；全局清理任务仍可处理已撤销凭据、已结算请求和法定保留数据；
- 不再创建新的请求 Lease 或占用新的并发槽；暂停前已准入的 Lease 在请求完成、取消或 TTL 到期后正常结算释放；
- 现有成员身份、设备凭据、容量配置和历史数据保留；
- 已认证成员仍可查看 Team 控制面；
- 普通成员仍可主动退出；
- 成员仍可新增、更新或撤销自己提供的容量，但暂停期间任何容量都不承接新请求；
- Owner 仍可撤销邀请码、移出成员、转让所有权、恢复或解散 Team。

“低资源休眠”不等于零存储：成员、加密凭据、审计、恢复记录和终态诊断仍按各自保留规则保存。用户主动打开自己的容量页面或执行容量管理时，可以按需进行必要的 Provider 校验；暂停提交前已经发出的自动读取排空后，闲置的暂停 Team 不得继续产生自动 Provider 读取。

暂停确认文案：

> 暂停 Team？
> 暂停后，Team 不再接收新请求，也不能加入新成员。现有成员和设置会保留，正在进行的请求不会被中断。

按钮：`确认暂停`

### 13.3 恢复效果

- 恢复不是破坏性操作，可直接确认执行；
- 恢复后允许新的共享请求；
- 恢复后首次请求准入必须按当前 Provider 状态重新校验容量；暂停前缓存的`observedLifecycleRevision`必然早于恢复后的当前 revision，不能直接放行；
- 尚未到期且未撤销的邀请码重新可用；
- 不恢复已过期、已撤销或已使用的邀请码。

成功提示：

> Team 已恢复，新请求和仍有效的邀请码现在可以继续使用。

## 14. 解散 Team

### 14.1 产品语义

解散是不可恢复的 Team 级终止操作，只能由当前 Team Owner 发起。

解散不是：

- 暂停 Team；
- Owner 退出；
- 删除 Owner 本机配置；
- 直接物理删除数据库中的 Team 记录。

### 14.2 确认要求

确认界面必须：

- 展示 Team 名称；
- 列出成员、邀请码、设备凭据和容量后果；
- 要求用户输入完整 Team 名称；
- 只有完全匹配时启用最终按钮；
- 使用明确按钮文案`永久解散 Team`。

确认文案：

> 永久解散「Design Team」？
> 所有成员都会立即无法访问 Team，全部邀请码会失效，Team 不再接收新请求。此操作不可恢复。

### 14.3 服务端事务结果

解散的服务端持久化阶段必须原子完成：

1. 从调用凭据只读解析候选 Team ID，不据此做最终授权；
2. 先锁定 Team；
3. 在 Team 锁内重新验证凭据仍有效、调用者仍是唯一 Team Owner，且 Team 处于`active`或`paused`；
4. 将 Team 原子置为已解散终态，阻止新的邀请、加入、成员变更和请求准入；
5. 取消待处理的所有权转让请求；
6. 按稳定 ID 顺序撤销全部未使用邀请码并覆盖其有效摘要；
7. 按稳定 ID 顺序终止全部活跃成员身份；
8. 按稳定 ID 顺序撤销全部 Team 设备凭据，包括发起者当前凭据，并创建诊断 tombstone；
9. 按稳定 ID 顺序将全部 Team 贡献标记为已撤销；
10. 写入 Team 解散审计事件和幂等操作结果；
11. 提交后返回无秘密、可幂等确认的解散结果。

提交后：

- 不再准入新的共享请求；
- 已准入请求允许完成和结算；
- 外部 Broker 或上游凭据清理由后台重试；
- 外部清理失败不能恢复 Team，也不能把已提交的解散伪装成失败；
- 晚到的容量写入、OAuth 完成回调或上游清理回调必须在 Team 锁内重新看到`dissolved`，不得重新激活贡献、保存可路由凭据或恢复任何访问；必要的秘密只能进入清理流程；
- 保留必要的审计、使用和结算 tombstone；
- 解散不影响成员自己的 Codex 账号本身。

解散后拒绝的是新的用户业务请求和用户发起的 Team、成员、邀请、设备或容量管理变更；已准入请求结算、后台凭据清理、审计维护、终态查询和操作 ACK 仍被允许，但不得改变 Team 终态或恢复访问。

### 14.4 超时与幂等

解散会撤销发起者自己的 Team 凭据，因此必须专门处理响应丢失：

- 提交解散前，Host 生成随机的操作 ID 和至少 256 bit 的恢复秘密并安全保存；
- 已认证的解散请求携带操作 ID 和恢复秘密摘要，服务端在解散事务中持久化幂等结果；
- Team 凭据撤销后，Host 仍可凭`操作 ID + 恢复秘密`访问仅返回该次解散结果的专用查询端点；它不能读取 Team 数据或发起其他操作；
- 相同操作的重试或结果查询必须返回同一最终结果；若服务端尚无该操作记录且原凭据仍有效，Host 可用相同操作 ID 重试原请求；
- 客户端超时时进入`正在确认解散结果`，不能直接清理本机状态；
- 确认解散后，Host 先持久化无秘密的本机终态标记并停止使用旧连接，再显式 ACK；ACK 响应丢失时以相同操作重复 ACK，确认后才删除恢复秘密，记录保留遵守 §17.3；
- 清理本机凭据独立重试，不阻塞 ACK。可写存储删除失败时展示`Team 已解散，本机连接清理待重试`；只读环境变量来源提示手动清理，均不能把本地清理失败误报成远端解散失败。

### 14.5 解散后的成员设备

- 所有 Team 请求均被拒绝；
- 服务端必须通过 §17.4 的 Key 诊断 tombstone 返回 Team 已解散终态，而不是通用连接错误或“Team 已暂停”；
- Host 展示：`这个 Team 已永久解散，无法继续访问。`；
- 唯一可用操作为`清除本机连接`或只读配置清理说明。

## 15. 设备连接

### 15.1 与成员身份的关系

- 一个成员可以拥有一个或多个设备凭据，但本规格不提供完整设备列表 UI。
- 当前 Host 同一时间最多保存一个正式 Team 连接。
- 加入 Team 会创建成员身份及该 Host 的首个设备凭据。
- 删除本机凭据不会自动删除远端成员身份。

### 15.2 普通 UI

普通 UI 只提供：

- 成员主动退出；
- Owner 转让或解散；
- 本机凭据已经失效时的`清除本机连接`。

“断开此设备但保留成员身份”放在高级能力中，在重新连接和设备凭据管理闭环完成前不作为主路径展示。

### 15.3 最后 Owner 访问保护

- `服务端有效 Owner 凭据`指凭据记录未撤销、未到期、属于当前活跃 Owner，且按当前认证策略处于可认证状态。该条件可在事务内由服务端数据确定，但不等于证明某台 Host 此刻仍保存其明文。
- `本次持有证明`指一份凭据成功认证当前请求，并在 Team 锁内重新验证后仍为服务端有效。近期使用时间、只有数据库摘要或另一份未参与本次认证的凭据都不能替代本次持有证明。
- 每个`active`或`paused` Team 在每次服务端事务提交后必须至少有一份服务端有效 Owner 凭据；初始化必须原子创建首位 Owner 及其首份凭据。服务端不声称能够防止用户在事务外遗失所有本机秘密，凭据备份或人工恢复不属于本版能力。
- 当前版本的 Owner 凭据不得自动到期。未来若增加到期、策略禁用或后台轮换，它们都按凭据状态写操作处理，不能绕过本节不变量。
- 所有可能改变当前 Owner、转让来源成员或目标成员服务端有效凭据的签发、撤销、策略变更、成员终止和转让操作，都必须按`Team → 成员 → 设备凭据`锁定，并在同一事务内重新计算角色和有效凭据。
- 普通撤销 API 不允许撤销认证当前请求的 Owner 凭据。Owner 如需撤销当前设备，必须先用另一份 Owner 凭据认证该操作，从而对提交后保留的凭据提供本次持有证明；安全的所有权转让或 Team 解散走各自专用流程。
- 最后一份服务端有效 Owner 凭据只能在同一原子事务完成安全的所有权转让或 Team 解散时失效。
- 两个并发撤销请求不得各自通过旧计数检查后同时撤销最后两份凭据。
- 目标成员接受转让时必须用自己的目标凭据完成本次持有证明；该凭据在角色交换提交后成为服务端有效 Owner 凭据。它与目标最后一份凭据撤销并发时，先获得 Team 线性化点者生效；若转让先完成，后到撤销必须遵守新 Owner 的最后凭据保护。
- 服务端不可达时，不提供“只删除本机副本”作为常规操作。

## 16. 用量、账号共享边界与成员生命周期

### 16.1 用户概念

- `容量`是后端路由层对“某个贡献账号当前是否可以承接请求”的技术概念，不代表已经消费的金额、Token 数或余额。由于这一词义会让普通用户误解，Browser 的一级导航不再使用`容量`。
- 用户查看已经发生的消耗时进入`用量`。个人账号是否共享给 Team 继续由现有 Codex 账号管理区负责；Team 设置不再重复展示`我的共享`摘要、共享开关或管理按钮。消费指标和共享设置不得混成一个`容量`概念。
- 现有界面中的`共享账号`管理模块和`保护策略`可编辑字段分别属于个人共享来源和该来源的使用限制，只在 Codex 账号管理区出现，不是成员角色或 Team 设置；用量页、成员页和邀请码页不展示这些管理入口。暂停、退出、移出和解散等生命周期确认仍可说明它们对账号共享的影响。
- Team Owner 和普通成员都可以管理自己的共享，但不能查看或修改其他成员的原始 Codex 凭据。共享操作不会影响用户在 Team 之外使用自己的 Codex 账号。
- 成员列表不展示共享来源、Provider 额度、并发保护或使用限制。

### 16.2 本版用量语义

- Browser 用量页只展示三个用户指标：`预估费用（USD）`、`Token 用量`和`请求次数`。`Credits`继续作为 Host 内部准入与保护单位，但不得进入 Browser DTO、页面或由 Browser 换算成金额。
- 只有 Provider 返回满足`0 ≤ cached_input_tokens ≤ input_tokens ≤ 1_000_000_000`且`0 ≤ output_tokens ≤ 1_000_000_000`的合法整数用量时，该 attempt 才算 Token 已计量；字段缺失、越界或关系非法不能通过截断、钳制或猜测伪造成合法值。`totalTokens = input_tokens + output_tokens`，缓存输入已经包含在 input 中，不能重复相加；输出包含 reasoning Token。
- Host 在结算时用实际可定价的 Provider、模型和服务档位匹配本地版本化价格表，并按未缓存输入、缓存输入和输出分别计算 API 标价等价估算。币种固定为 USD，持久化为整数 micro-USD 与`pricingCatalogVersion`；价格版本按请求准入时间选择，历史估算不得随未来价格表更新而静默重算。
- `预估费用（USD）`不是 Provider 权威账单、订阅实付、账户扣款、订阅余额或成员账单。若未来获得 Provider 权威账单，必须新增独立的`实际费用`语义，不能覆盖或混入历史预估值。
- 原始输入、缓存输入和输出 Token 只允许在 Host 结算时短暂校验和计算；持久层仅新增每个 attempt 的聚合`totalTokens`、可空的`estimatedCostUsdMicros`和价格版本，Browser 只接收时间窗口汇总，不接收逐请求记录或 Token 拆分。
- 若 Token 合法但实际模型、服务档位或价格版本无法可靠匹配，Token 可以计量，费用保持不可用；不得套用近似模型价格。若 Provider 没有返回合法 Token，Token 与费用都保持不可用，请求次数仍然统计。
- 本页只统计`consumerMemberId != upstreamOwnerMemberId`的跨成员共享 attempt；成员使用自己贡献账号的 self-use 不属于 Team 共享用量，继续由普通账号页表达。`我的用量`按`consumerMemberId = 当前成员 ID`归属；`Team 总用量`包含窗口内全部跨成员共享 attempt，并包含 Owner 自己的子集，因此两个数字不能相加。
- `请求次数`统计已经准入的跨成员共享上游 attempt；重试分别计数，不能称为“完成请求”“成员提问数”或对话数。每个汇总必须分别保留`requestCount`、`tokenMeasuredRequestCount`和`pricedRequestCount`，Token 只求和已计量 attempt，费用只求和已定价 attempt。
- `requestCount = 0`时可以可靠显示`US$ 0.00 / 0 Token / 0 次请求`；`requestCount > 0`但相应覆盖为 0 时，Token 或费用显示`—`；任一覆盖小于请求数时只能把已有数字标为`部分数据`。Token 与费用覆盖相同可合并为`已计量 X / Y 次`，覆盖不同时必须分别表达，不能把部分小计伪装成完整总量。
- Team Owner 可以查看`Team 总用量`和自己的子集；普通成员只查看自己的汇总。任何角色都不在本页看到逐条请求、提示词、回复、文件、原始错误、其他成员排行或其他成员的个人明细。
- 页面默认以明确时间窗口展示汇总；attempt 及其随后结算的 Token 与费用永远按权威`admittedAt / startedAt`归入原窗口，不能因晚结算移动到`finishedAt`所在日期。聚合请求失败时显示`暂时无法获取用量`，不能用旧缓存、占位百分比或推测值替代。
- Team 暂停后仍可查看用量。暂停前已经准入的请求完成结算后，用量仍可能更新；这不表示暂停后又准入了新请求。
- Provider 剩余百分比若可获得，只能作为贡献者本人共享来源的近期信号展示；它不是 Team 总余额、精确剩余 Token、剩余请求数或金额，也不能据此绘制 Team “已用/剩余”进度条。
- 每日共享 Credits 上限仍属于 Host 内部准入保护配置；Browser 不展示 Credits，也不得根据预估费用或 Token 反推出“今天还剩多少容量”。

### 16.3 个人账号共享生命周期

- Codex 账号管理区只列出当前成员自己连接给 Team 的来源、是否允许共享及自己的限制；Team 设置只消费完成用量和路由所需的最小投影，不重复提供个人共享编辑入口。其他成员连来源数量和实时可用性都不可见。
- Team Owner 和普通成员都可随时开始、停止或调整自己的共享。停止共享只阻止该来源承接新的 Team 请求，不退出 Team，也不会影响自己的 Codex 账号。
- Team 暂停期间仍可编辑个人共享；配置被保存但不可路由，恢复后按当时的有效配置和最新 Provider 状态重新参与。
- 移出、退出和解散会停止相关容量承接新请求。
- 已准入请求允许完成并结算，之后再清理上游授权。
- Team 暂停会停止全部新的 Team 共享请求，但不会删除容量配置。
- 定时容量监控必须同时检查容量状态与所属 Team 状态，只为`active` Team 中的`active`容量发起新刷新；不能因为容量记录仍为`active`而继续轮询已暂停 Team。外部 Provider I/O 不得持有 Team 数据库锁；所有容量快照、缓存项和共享的 in-flight 结果必须携带发起读取时的`observedLifecycleRevision`，跨 Host 也不能把该标签省略或改写成较新 revision。
- 缓存写入不是权限或准入边界。最终请求准入必须在 Team 共享锁内同时确认`status = active`且候选容量的`observedLifecycleRevision = current lifecycleRevision`；任一不匹配都不得创建最终容量预留或使用事件。服务端应释放 Team 锁，在锁外按最新 revision 强制读取 Provider 后重新进入完整准入流程；重试期间 revision 再变化则继续拒绝旧结果，不能持有数据库锁等待外部 I/O。
- Team 暂停期间成员仍可新增、更新或撤销自己的容量配置；OAuth 完成回调可以完成安全登记，但必须在 Team 锁内确认状态，保持不可路由，直到 Team 恢复。

## 17. 工程安全与一致性约束

### 17.1 秘密与权限边界

- 邀请码、Team Key、OAuth 凭据不得写入日志、URL 查询参数、审计详情或 Browser 持久化状态；邀请码在 Browser 中的短暂例外遵守 §2.4。
- 邀请码必须由 CSPRNG 生成并至少包含 256 bit 随机熵。服务端保存用于查找和接受的安全摘要，并另存用于 Owner 再次查看的 AEAD 认证加密密文；不得保存可直接读取的明文。
- 每条邀请使用独立随机 DEK 和 nonce，以 AES-256-GCM 加密邀请码；DEK 再由版本化 invite KEK 包裹。AAD 使用带长度或 canonical JSON 的无歧义编码，至少绑定 domain=`dsh-team-invite-token/v1`、`teamId`、`inviteId`、`createdAt`的 UTC epoch milliseconds 和`tokenDigest`。记录包含 envelope version、key ID、wrapped DEK、nonce、ciphertext 与 tag；解密后必须重算摘要并恒定时间比对。摘要、完整 envelope 和邀请元数据必须在同一生成事务中写入，任一失败都不得创建可用邀请。
- 邀请密文由 Team Host 专属的`InviteCipherProvider`负责，不得复用或下放给保存 OAuth / Provider 凭据的 Credential Broker。配置使用独立的`inviteTokenMasterKeyRef`和可读历史 key refs；即使`credentialBroker = remote`也只由 Team Host 解析。invite KEK 不得与 OAuth `credentialMasterKeyRef`、Broker API key、bootstrap token、Team API Key 复用或相互派生；该秘密不得进入 Browser、Edge、Broker、PostgreSQL 或补丁生成日志。多 Host 必须加载同一组当前/历史版本，先部署可读新旧版本的 key ring，再切换写入版本；缺少当前写入密钥时禁止生成，缺少对应历史密钥时再次查看安全失败，但摘要接受路径仍保持可用。旧 reader key 只有在数据库证明不再被任何未终态 envelope 引用后才能删除，保留窗至少覆盖最长 30 天有效期与 24 小时到期清理窗。
- 请求处理期间不得在持有 Team 数据库锁时调用外部 Broker、KMS 或 secret manager。Team Host 必须在开始承接请求前把可用 invite key ring 安全加载到 Host 内存，并只用本地 provider 完成加解密；启动、刷新或轮换无法获得所需密钥时进入上述安全失败状态。这样再次查看可以在同一 Team-first 临界区内完成实时 Owner 校验、邀请状态复核、解密和审计线性化，而不会把数据库锁跨到外部 I/O。
- 密钥轮换对既有邀请只解包并重包 DEK，不解密邀请码。重包裹先取得 Team→invite 锁并按`secretRevision`比较更新；若在准备期间邀请已使用、撤销、过期、因转让失效或 Team 已解散，终态清除获胜，轮换不得重新写回 envelope。
- 再次查看使用独立的 Owner-only 显式非缓存动作（例如 same-origin `POST /invites/:inviteId/reveal`），不得使用可被预取或共享缓存的普通 `GET`。接口先按 Team 验证实时 Owner 身份，再查邀请；响应必须`Cache-Control: no-store`并限速。Browser 在关闭弹窗、切换页面、文档进入隐藏态、检测到角色或连接变化时立即清除组件内明文；单次明文查看窗口最长 60 秒，窗口到期必须自动关闭并清除，即使尚未检测到另一台 Host 上的角色变化。每次重开均重新请求和鉴权。邀请码不得藏在列表 DOM、初始 HTML、URL、客户端状态持久化、错误、日志或遥测中。
- 中央 Team API 与本地 Host 代理都使用单条显式`POST`再次查看接口；请求只携带 invite ID，成功结果只含`inviteId + inviteToken + expiresAt`，普通 Owner 列表仅含`inviteId + label + createdAt + expiresAt + revealable`等无秘密元数据。终态、过期、不可解密和不存在的邀请对已认证 Owner 返回统一 unavailable 形状，不泄露内部原因；普通成员在资源查找前得到同形`403`。两跳均设置`Cache-Control: no-store`，Browser fetch 使用`cache: no-store`。
- 再次查看必须在 §17.2 的 Team 线性化边界内复核邀请仍为待用且未过期。若查看先提交，随后发生的使用、撤销、转让或解散仍可使已经返回的码立即失效；若终态变更先提交，则查看拒绝且不返回明文。暂停不是邀请终态，当前 Owner 暂停期间仍可查看。
- 邀请一旦使用、撤销，或因 Owner 转让、Team 解散而失效，提交该终态的同一事务必须清除其可解密密文并保留不可逆摘要或最小审计信息。到期在`serverNow >= expiresAt`时立即阻止再次查看和接受；预览、接受、再次查看或列表触及该邀请时都在 Team-first 锁内惰性清除。后台清理器先无锁收集候选 team ID，再逐 Team 锁定 Team 行，并按 invite ID 升序锁定过期候选、复核服务端时间后清除 envelope；不得先锁 invite。物理清除最迟在`expiresAt + 24 小时`前完成。审计只记录查看动作的 actor、invite ID 和时间，不含邀请码。密文损坏或密钥不可用时安全失败，不回显错误明文；已持有码仍可按摘要使用，Owner 可撤销并重新生成。
- 邀请码预览只返回 Team 名称、邀请说明、到期时间和 Team 状态，不回显邀请码。
- 预览和接受接口必须限速；已使用、过期、撤销、所属 Team 已解散、未知和格式错误使用相同的无效响应。
- 普通成员的 Team 概览不得包含邀请码元数据。
- Owner-only 的邀请和成员管理接口必须先确认调用者 Team 角色，再对目标资源给出结果；普通成员请求存在或不存在的资源 ID 都返回同形 `403`，不能形成存在性探测。
- 成员显示名称不应被当作认证主键。
- Host 必须从实际监听配置建立固定的本地 Origin / Host allowlist，不能从请求的`Host`头动态推导“同源”。仅检查 loopback remote address、`Origin.host === Host`或`Sec-Fetch-Site != cross-site`都不足以防止 DNS rebinding。所有 Browser 发起的 Team 写操作，以及生成或返回秘密的操作（包括邀请码再次查看），必须同时满足：请求`Host`与`Origin`精确匹配固定 allowlist；受保护方法缺失`Origin`即拒绝；浏览器提供时`Sec-Fetch-Site`必须为`same-origin`；并携带由 Host 在受信同源 bootstrap 中签发的不可猜 CSRF/session capability。capability 必须绑定该 Host 进程或短时会话、可轮换并在重启或到期后失效，不得出现在 URL 或日志中。任一校验失败均在读取 Team 或邀请资源前返回同形`403`。输入 Team 名称只用于降低误操作，不构成身份验证或授权。
- Team 已解散后，任何旧角色、旧 Key 或旧邀请码都不能恢复访问。
- `joinLocator`必须使用带版本的非对称数字签名；私钥可以轮换，但验证历史 locator 所需的旧公钥必须长期保留。公钥和签名版本的保留期不得短于 §17.3 加入提交标记的查询期；本版允许离线 Host 无期限恢复，因此两者均不得设置导致历史查询失真的普通 TTL。

### 17.2 Team 写操作的唯一线性化顺序

以下操作必须进入同一 Team 级串行化边界：邀请码生成、再次查看、接受、加入取消、撤销和到期密文清理，成员移出和退出，所有权转让的发起、接受、拒绝、撤销、到期和自动取消，暂停和恢复，设备凭据签发和撤销，容量贡献创建、更新和撤销，OAuth 完成回调，Team 解散，以及共享请求准入。

统一顺序为：

1. 只读解析目标 Team ID，不据此返回敏感资源是否存在；
2. 先锁定 Team 行；请求准入可使用与生命周期写锁互斥的 Team 共享锁，其他写操作使用排他锁；
3. 在 Team 锁内重新验证凭据、当前成员、当前角色和 Team 状态；
4. 如需子资源，依次按`所有权转让请求 → 邀请 → 成员 → 设备凭据 → 容量贡献 → 可恢复操作记录`锁定，同类多行按稳定 ID 升序；
5. 在提交前再次验证本操作的不变量。

接受邀请码时，可以先用令牌摘要只读定位 Team，但必须随后先锁 Team、再锁邀请，并在锁内重新验证摘要、到期时间、状态和 Team 状态。不得保留现有的`先锁邀请、再锁 Team`路径。

并发结果以先获得 Team 线性化点并提交的操作为准：

| 并发场景 | 前者先提交 | 后者观察到的结果 |
| --- | --- | --- |
| 接受邀请码 → 暂停 | 成员加入成功 | Team 随后暂停 |
| 暂停 → 接受邀请码 | Team 先暂停 | 加入拒绝，邀请码不消费 |
| 生成邀请码 → 暂停 | 邀请生成成功 | 邀请保留但暂停期间不可使用 |
| 暂停 → 生成邀请码 | Team 先暂停 | 生成拒绝，不创建邀请 |
| 查看邀请码 → 使用、撤销、转让或解散 | 查看先返回当前有效码 | 后续终态正常提交，已返回码随即失效 |
| 使用、撤销、转让或解散 → 查看邀请码 | 邀请或 Team 终态先变化 | 查看拒绝且不返回邀请码明文 |
| 暂停 → 查看邀请码 | Team 先暂停但邀请仍待用 | 当前 Owner 仍可查看；页面同时提示暂停期间不可加入 |
| 到期清理 ↔ 查看或接受邀请码 | Team-first 锁内以服务端时钟判定 | `serverNow >= expiresAt`时查看和接受均拒绝，清理只删除密文且不改变已到期事实 |
| 接受邀请码 → 撤销邀请码 | 成员加入成功 | 撤销看到邀请码已使用 |
| 撤销邀请码 → 接受邀请码 | 邀请先撤销 | 加入拒绝，邀请码不消费 |
| 生成邀请码 → 完成 Owner 转让 | 邀请先生成 | 转让事务将其一并撤销 |
| 完成 Owner 转让 → 旧 Owner 生成/撤销 | 角色先变化 | 旧 Owner 统一返回 `403` |
| 完成 Owner 转让 → 接受旧邀请码 | 转让先撤销全部待用邀请 | 加入拒绝，邀请码不消费 |
| 目标接受转让 → 目标最后 Key 撤销 | 转让先完成 | 撤销按新 Owner 最后凭据保护拒绝 |
| 目标最后 Key 撤销 → 目标接受转让 | 凭据先撤销 | 接受失败，双方角色不变 |
| 请求准入 → 暂停或解散 | 请求先获准 | 该请求允许完成 |
| 暂停或解散 → 请求准入 | 状态先变化 | 新请求被拒绝 |
| OAuth 完成回调 → 解散 | 容量先安全登记 | 解散将贡献和凭据一并终止 |
| 解散 → OAuth 完成回调 | Team 先进入终态 | 回调不得激活贡献，秘密进入清理或安全丢弃 |

解散先提交时，所有后续用户业务请求和用户发起的 Team 写入均拒绝；其他操作先提交时，解散事务必须看到其结果并完整终止或撤销，不得遗漏刚创建的成员、邀请码、Key 或容量贡献。终态查询、ACK、已准入结算和后台清理只可按 §14.3 继续，不能恢复 Team。

### 17.3 可恢复操作协议

- 退出、解散和加入恢复使用的操作 ID 必须由 CSPRNG 生成，随机熵不少于 128 bit。
- 恢复秘密必须与 Team API Key 分离并至少包含 256 bit 随机熵；它只用于该操作的查询、取消和 ACK，永远不能认证 Team API。
- 操作记录必须绑定`operationType + teamId + actorMemberId 或预备 Key ID + requestBodyHash + recoverySecretDigest`；加入操作还必须绑定`joinLocator + inviteDigest + normalizedDisplayName + candidateKeyDigest`，不持久化邀请码明文。
- 接受加入的同一事务还必须写入不可变的最小提交标记，至少包含`teamId + inviteId + attemptId + operationId + acceptedAt`，不包含邀请码、恢复秘密、Key 或成员资料。每份一次性邀请最多一条该标记，因此其数量只随真实成功加入增长，不受预览或取消刷量影响。
- 加入提交标记不属于可回收的完整操作结果，普通结果 ACK、Team 解散、邀请摘要覆盖和结果压缩都不能删除它。本版对历史 locator 提供无期限恢复，因此标记无普通 TTL；若未来引入数据擦除期限，期限结束后只能返回`unknown_or_unauthorized`，不得在标记缺失时声称`expired_no_commit`。
- 已认证的相同操作重试只有在全部绑定字段一致时才幂等返回原结果；相同操作 ID 携带不同作用域、正文或恢复摘要时返回 `409`，且不执行任何变更。
- 单用途结果查询只返回操作类型、状态和粗粒度终态，不返回 Team 数据；错误恢复秘密与不存在的操作使用同形响应并统一限速。§9.4 的无副作用加入回收只有在服务端验证签名 locator 内的操作 ID 与恢复摘要后才能返回`expired_no_commit`，不构成绕过。
- 结果查询和 ACK 都可重复，不得一读即销毁。Host 只有在将远端终态持久化为本机无秘密状态后才 ACK；ACK 确认后才删除恢复秘密。唯一例外是 §9.4 已回收操作行后的`expired_no_commit`：签名 locator 与恢复秘密构成无副作用证明，服务端没有待 ACK 资源，Host 持久化证明后即可清理。
- 除 §9.4 明确允许回收的无副作用加入结果外，未 ACK 的终态结果不得因固定 TTL 直接删除；终态 30 天后可压缩为只含绑定摘要、终态和时间的最小 tombstone，并保留到 ACK。ACK 后再保留至少 24 小时宽限期，以承受 ACK 响应丢失。加入完整结果的清理不影响上述独立提交标记。
- 未认证加入 attempt 使用按 invite 与来源限速的独立存储和配额；单份邀请同一时刻最多一个未过期槽，不能用不同操作 ID 无限占位。该配额与已认证成员操作、Owner 操作隔离，耗尽时只能拒绝新的加入 attempt。
- 已认证成员退出和 Owner 解散必须拥有独立预留的结果槽：成员退出使用该成员的单一终止槽，Team 解散使用该 Team 的单一终态槽。它们不得因为加入 attempt 或普通可恢复操作配额已满而被拒绝；存储异常仍按结果不确定处理并告警，不能伪装成功。
- 其他可恢复操作的创建和查询仍须按 Host、来源和 Team 限速并设置未完成操作配额；达到配额时拒绝对应命名空间的新操作，不能删除已产生副作用的未 ACK 结果来腾出空间。
- 恢复秘密只保存在 Host，不得下发 Browser、进入 URL、日志、审计或遥测；它不能认证任何 Team API。

### 17.4 已撤销 Key 的终态诊断

- 撤销 Team Key 时，服务端保留不可逆的安全摘要到`teamId + memberId + terminalReason`的诊断 tombstone；从撤销时起保证至少保留 365 天，部署的数据保留策略可以延长但不能缩短该窗口。
- 诊断 tombstone 不能恢复认证、读取 Team 数据或执行操作；它只能让持有旧高熵 Key 的 Host 获得粗粒度终态：`member_removed`、`member_left`、`team_dissolved`或`device_revoked`。
- 在保证窗口内，能匹配 tombstone 的旧 Key 必须返回 `410`和终态枚举；完全未知的 Key 返回通用 `401`。窗口结束后服务端可继续返回终态，也可按数据保留策略退化为通用 `401`。
- 邀请码在使用、撤销或解散后不提供这种诊断，其摘要按邀请规则覆盖或删除，后续统一返回“邀请码无效或已失效”。

## 18. 审计要求

服务端必须记录以下成功事件：

- Team 初始化；
- 邀请码生成；
- 邀请码被再次查看；只记录 actor member ID、invite ID 和服务端时间，不记录邀请码，Browser 本地复制不作为服务端审计事件；
- 邀请码撤销；
- 邀请码被接受；
- 成员加入；
- 成员被移出；
- 成员主动退出；
- 所有权转让已发起、已拒绝、已撤销、已到期、自动取消或已完成；
- Team 暂停；
- Team 恢复；
- Team 解散；
- 两角色与显示名称迁移。

审计记录不得包含完整邀请码、Team Key、OAuth 凭据、账号邮箱、请求提示词或模型输出。

本规格不要求在 Browser 中提供审计页面，但后端事件必须可供后续运维和调查使用。

## 20. 信息架构约束

本规格只约束功能分组，不规定最终视觉样式。

已加入后的 Team 工作区包含：

- `用量`：展示服务端可证明的预估费用（USD）、Token 用量、请求次数和紧凑的数据状态；Team Owner 可看`Team 总用量`与`我的用量`，普通成员只看`我的用量`；
- `成员`：Team Owner 和活跃成员；
- `邀请码`：仅 Team Owner 可见。

Browser 不再单独展示一组“个人”导航：

- 个人账号共享沿用现有 Codex 账号管理入口，Team 工作区不再重复展示摘要、共享开关或管理按钮；
- 当前用户的 Team Owner / 成员身份直接显示在 Team 头部，不再设置`我的 Team 身份`页。

Team 头部展示：

- Team 名称；
- 运行状态；
- 当前用户角色；
- 与当前角色匹配的 Team 管理菜单。

待处理的所有权转让不进入成员行菜单：当前 Owner 在`所有权`菜单中查看并撤销；指定目标在 Team 头部看到接受/拒绝提示；其他成员完全不可见。

当前用户的成员关系从 Team 头部的管理菜单进入：

- 普通成员只看到`退出 Team`，不得看到暂停、转让、解散或邀请管理；
- Team Owner 看到“Owner 不能直接退出，请先转让或解散”的说明以及 Team 级操作；
- 退出后的本机清理是远端终态确认后的后续步骤，不与解散混成一个操作。

Team 管理菜单按作用范围分组：

- Team Owner 可见`Team 运行`：暂停或恢复；
- Team Owner 可见`所有权`：转让 Team Owner；
- Team Owner 可见`Team 生命周期`：永久解散 Team；
- 普通成员只可见`成员关系`：退出 Team。

邀请文案区分意图与执行动作：成员页的 Owner 主按钮为`邀请成员`；进入邀请码页或弹窗后，实际创建凭据的按钮为`生成邀请码`。

以下内容不得混入成员或邀请码页面：

- 一次请求如何路由的教程；
- 预估费用、Token 用量、请求次数和数据状态；这些汇总只属于`用量`页；
- 逐条请求记录、模型或成员排行、提示词、回复和原始路由活动；
- 原始服务器地址；
- Team Key 或 OAuth 技术信息；
- 本机断开、成员退出和 Team 解散的混合“危险区”。

## 21. 当前实现迁移要求

本节用于说明目标规格与现有实现的已知差距，不是实现计划。

### 21.1 两角色迁移

- 任何写入前先对每个`active`或`paused` Team 预检：恰好一名活跃 Owner，且该 Owner 至少一份 §15.3 定义的服务端有效凭据。零 Owner、多 Owner 或无服务端有效 Owner 凭据时，该 Team 的迁移必须无写入地阻断并报告 Team 与冲突成员 ID，不能猜测或静默指定 Owner。
- 迁移只能依据服务端凭据记录做上述预检，无法也不得声称证明某台 Host 仍持有明文。服务端有效凭据存在但用户已经遗失所有本地秘密时，Team 可能在操作上失联；凭据备份、人工恢复或运维解散必须作为本规格之外的独立能力处理，迁移不能静默伪造新凭据。
- 通过预检后，每个 Team 在单一事务中完成角色、邀请和名称迁移；任一步失败则该 Team 全部回滚。
- 新写入的角色只允许 `owner | member`；现有唯一 Owner 保持 Owner，现有活跃 `admin` 迁移为`member`，普通成员及其容量归属保持不变。
- 原子撤销所有`invited_by_member_id`不是当前 Owner、创建者缺失或无法验证的待使用邀请码并覆盖摘要；只有当前 Owner 创建且仍满足新规则的邀请码可以保留，防止旧 Admin 或历任 Owner 使用已保存的旧码继续拉人。
- 旧版本仅保存摘要、无法恢复明文的当前 Owner 待用邀请码可以继续用于已经分发的码，但必须投影`revealable = false`并在 Owner 列表显示`旧邀请码无法查看，请撤销后重新生成`；迁移不得伪造、猜测或静默替换邀请码。迁移完成后新生成的邀请码必须满足 §17.1 的加密存储和再次查看规则。
- 在开放新版邀请生成前，每一台 Team Host 都必须成功加载相同的版本化 invite key ring 并通过本地加解密自检；不满足时邀请生成与再次查看保持关闭，不能降级为数据库明文或把 invite 密钥交给 Credential Broker。数据库迁移只给 Team Host 运行身份授予邀请密文字段权限，Broker 运行身份不得获得`team_invites`或其他控制面表权限。
- PostgreSQL 邀请表新增可空的 envelope version、key ID、wrapped DEK、nonce、ciphertext 和 tag 字段，并以全有或全无的数据库约束防止半份密文；这些字段全为 NULL 只表示升级前`revealable = false`的摘要-only 邀请。迁移顺序为先加可空 schema，再配置并滚动全部 Team Host，最后才启用新版邀请生成；滚动窗口内旧 Host 不得继续生成摘要-only 新邀请。
- 迁移提交后立即失效所有角色与授权缓存；邀请、移出、暂停和 Team 生命周期接口始终按实时角色判断，旧 Admin 请求不能凭缓存继续成功。
- 删除或永久拒绝通用角色修改 API；所有权转让只走 §12 的两阶段流程。
- 历史审计中的`admin`和`role_changed`保留读取能力，但不能再产生新记录；迁移写入专用审计事件。
- 当前 Owner 首次进入时看到一次性说明：`Team 角色已简化为 Team Owner 和成员；旧 Admin 已变为成员，非当前 Owner 创建的待用邀请码已撤销。`旧 Admin 首次进入时看到自己的当前角色说明。

### 21.2 显示名称迁移

- 迁移使用 §3.3 固定的 Unicode 15.1.0 规则计算规范化显示值和比较值。
- 旧值若规范化后为空、超长或含禁用字符，确定性改为`成员 · <stable-short-member-id>`；short ID 只来自非秘密稳定成员 ID，不使用邮箱或账号信息。
- 对同一 Team 的比较值冲突组，当前 Owner 优先保留原规范化名称；其余按`joinedAt 升序 → memberId 升序`排列。第一名保留基名，后续依次追加` · 2`、` · 3`，必要时按 Unicode scalar 截短基名，直到满足 120 长度且比较值唯一。
- 自动改名写入审计，并在受影响成员首次进入时展示一次性说明；显示名称不是身份，改名不改变成员、凭据或容量归属。
- 全部数据修复成功后才建立`(team_id, display_name_key) WHERE status = active`部分唯一约束；升级 Unicode 数据版本必须重新执行同等预检。

### 21.3 解散能力

- Team 状态需要增加不可恢复的解散终态。
- 生命周期表必须增加非空、单调递增的`lifecycleRevision`。新 Team 初始化为`1`；升级中的既有 Team 在维护锁内初始化为`1`后才重新开放生命周期写入，此后只允许按 §6.3 携带 expected revision 的比较并更新。
- 新增独立的 Owner-only 解散 API 和 Host 代理能力。
- 解散必须是服务端 Team 级事务，不能由前端清除本机配置模拟。
- PostgreSQL 必须覆盖真实升级迁移和全新安装。
- 解散与邀请接受、邀请生成、所有权转让、暂停和请求准入需要真实并发测试。

### 21.4 Browser 投影

- 普通成员概览中不再返回邀请码元数据。
- Owner 邀请列表只返回 invite ID、说明、创建/到期时间、暂停提示和`revealable`等无秘密元数据；完整邀请码只可由 §17.1 的显式再次查看动作单条返回，不得混入概览、列表、SSR 初始数据或批量响应。
- 成员行移除生成式头像。
- 删除 Admin 文案和升降级操作。
- 新增解散确认、当前 Host 结果确认中和终态页面；“确认中”不得投影为新的 Team 生命周期状态。
- 无秘密 Team 状态投影必须包含`lifecycleRevision`，Browser 发起暂停、恢复或解散时原样带回为`expectedLifecycleRevision`；该值用于并发控制，不需要作为用户文案展示。
- 活跃成员数必须基于实际活跃成员投影计算。
- 现有向任意成员返回全 Team `events + aggregates`的 usage API 必须替换为按认证角色塑形的 aggregate-only DTO；Browser DTO 不再包含逐条 event、成员 ID、贡献账号 ID、模型、状态或原始错误。普通成员的存储查询必须按`consumerMemberId = auth.memberId`裁剪；Owner 只获得 Team 共享总计和同样按自己消费方 ID 裁剪的个人总计，不能先拉取全量后仅靠 React 隐藏。
- Codex 账号管理区不能复用向所有成员列出全 Team contributions 的旧投影。Host/store 必须按`ownerMemberId = auth.memberId`裁剪，只返回当前成员自己的无秘密来源摘要与共享状态；Team 设置不得另设重复入口，其他成员连来源数量都不可见。
- 当前 Credits-only 事件表不能支持目标界面。必须新增前向数据库迁移，在 Host 结算时写入`totalTokens`、可空的`estimatedCostUsdMicros`和`pricingCatalogVersion`；不得回改已经发布的旧迁移，也不得由 Browser 或查询时临时把 Credits 换算成费用。
- 用量聚合 DTO 必须分别返回非负`requestCount`、`tokenMeasuredRequestCount`、`pricedRequestCount`，以及十进制字符串或`null`形式的`totalTokens`和`estimatedCostUsdMicros`；费用可用时`currency`固定为`USD`。这些字段用于区分可靠零、部分计量、Token 可用但价格未知和完全未计量；SQL 聚合不得把`requestCount > 0`的缺失值`COALESCE`成已知零。
- 价格表必须由 Host 持有并版本化。服务端无法证明请求使用的实际模型或服务档位可定价时，只结算 Token，不结算费用；当前请求中的模型字符串在完成生产验证前不能直接视为权威定价键。

### 21.5 旧连接入口

- 已有 Host Team Key 可以继续在 Host 凭据层认证，但不得再投影给 Browser。
- Browser 直接提交原始 Team Key 的旧`connect`入口必须删除或返回明确的永久拒绝；新加入只允许使用 §9 的邀请码预览 handle 与 Host 待加入流程。
- 旧`disconnect(false)`式“只删本机副本”不得作为有效连接的普通成功路径；成员退出必须确认远端终态。只有远端明确以 `401` 或 §17.4 的 `410` 拒绝旧 Key 后才能清除失效本机连接，服务端不可达不能伪装成已断开；设备撤销必须遵守最后 Owner 凭据保护。
- 只读部署配置不能由 Browser 修改，界面只提供无秘密的来源说明和手动清理指引。

### 21.6 低资源暂停与活动时间

- 权威`admittedAt`使用服务端时钟，并与该次新请求最终准入所需的容量预留及使用事件在同一事务提交。此前创建的临时路由 Lease 若因最终准入失败而被结算，不产生权威活动事件；重放、拒绝准入和后续结算不得新建或改写准入时间。
- Team 存储增加可空的`lastTeamRequestAt`单调摘要。它从逐请求权威事件异步取最大值，不写 Team 生命周期行、不递增`lifecycleRevision`；并发聚合只能保持或推进，不能倒退。未来自动休眠必须在 Team 排他锁内再次检查权威准入事件，不能只信可能滞后的摘要。
- 既有 Team 只在保留的权威使用事件足以证明成功准入时，回填对应的最大服务端准入时间；无法证明时保持为空，不伪造历史。未来启用自动休眠前必须为这类旧 Team 提供完整的新宽限期。
- 跨 Team 的定时容量查询必须过滤掉`paused`和`dissolved` Team；所有缓存快照和 in-flight 结果携带读取发起时的`observedLifecycleRevision`。允许保存旧结果用于诊断或观测，但只有 revision 与当前 Team 完全相等的快照才可能参与请求准入。
- 最终准入在 Team 共享锁内比较当前状态与 snapshot revision；不匹配时锁内不产生 Lease、最终容量预留或使用事件，锁外强制刷新后从头重试。这个准入时比较是单 Host、跨 Host 和`active r → paused r+1 → active r+2`的共同安全边界，不能依赖广播清缓存或写缓存前的一次状态读取。
- 暂停时无需删除容量或凭据；恢复后的容量缓存视为陈旧，并在首次准入前按当前策略刷新。

## 22. 验收标准

### SPEC-TEAM-001 — 角色不变量

- 系统只创建 `owner` 和 `member`。
- 每个 `active` 或 `paused` Team 恰好有一个活跃 Owner，`dissolved` Team 没有活跃 Owner。
- 每个有效 Team 在服务端至少有一份 §15.3 定义的有效 Owner 凭据；普通撤销不能撤销认证当前请求的 Owner 凭据，最后一份只能随安全转让或解散在同一事务内失效。
- 服务端测试只断言可验证的凭据状态和本次认证，不把数据库摘要或近期使用误当成某台 Host 仍持有明文的证明。
- 任何旧 Admin API 调用都不能获得管理能力。
- 每次实际生命周期转换恰好递增一次`lifecycleRevision`；相同操作 ID 重放不递增、不重复审计。
- Team 经`active → paused → active`后，携带旧 active revision 的暂停、恢复或解散请求返回`409`；`dissolved`永不重新激活。

### SPEC-TEAM-002 — 成员列表

- 不渲染头像。
- Owner 固定第一行。
- 只显示活跃成员，计数与行数一致。
- 普通成员看不到成员管理操作。
- 同一 Team 的活跃成员显示名称按 §3.3 唯一，控制字符、零宽默认忽略字符、空比较值和超过 120 scalar values 均被拒绝。

### SPEC-TEAM-003 — Owner-only 邀请

- 只有当前 Owner 可以生成、再次查看、复制和撤销有效邀请码。
- 普通成员直接调用存在或不存在的邀请资源 ID 都获得同形 `403`。
- 生成结果关闭后，Owner 可以从有效邀请码列表显式再次查看同一完整邀请码；完整码不直接出现在列表响应、列表 DOM 或持久化 Browser 状态中，关闭后清除且重开会重新鉴权请求。
- 再次查看与使用、撤销、转让和解散按 §17.2 线性化；后者先提交时不返回明文，查看先返回的码也会被后续终态正常作废。暂停期间可以查看，但不能生成或使用。
- 新邀请码的摘要和 AEAD 密文原子写入；不同邀请使用不同 nonce，AAD 篡改、密文损坏和错误密钥版本都安全失败且不返回明文；密钥轮换期间仍能查看全部未过期的新邀请码。
- 本地和远程 Broker 两种部署都由 Team Host 的独立`InviteCipherProvider`持有 invite key ring；Broker、Edge 和数据库均无法解密邀请码。多 Host 轮换按“先全部可读新旧版本、再切换写版本”执行；缺少当前密钥时生成与再次查看安全失败，且请求路径不在 Team 锁内访问外部 KMS 或 Broker。
- 使用、撤销、转让和解散在终态事务内清除密文；到期后立即禁止查看并在 24 小时内按 Team-first 锁序清除密文。旧摘要-only 邀请显示为不可查看并可由 Owner 撤销重建。
- 同一邀请码并发使用只能成功一次。
- 暂停时仍可凭码预览，但加入按钮禁用、服务端不消费；恢复后只有仍待用且未过期的码恢复可用。
- 所有权转让完成会撤销 Team 中全部待用邀请码；发起但尚未完成转让不会提前撤销。
- 邀请到期以服务端`now >= expiresAt`为边界，1/7/30 天按连续 24 小时计算。

### SPEC-TEAM-004 — 加入可恢复

- 预览不消费邀请码。
- Host 在远端预览前生成加入操作 ID 和独立恢复秘密；签名 locator 绑定其摘要。Browser 在 Host 建立短时预览会话后清除邀请码明文，只保留无秘密投影和本机 opaque handle；会话关闭或最长 15 分钟后清除。
- 加入成功始终创建普通成员。
- 加入操作使用相互独立的操作 ID、恢复秘密和候选 Team Key；查询、取消和 ACK 不能把候选 Key 当恢复秘密。
- 每份待用邀请同一时刻至多一个 15 分钟加入 attempt 槽；重复预览不增加槽，首个操作 ID 认领后不同操作 ID 冲突，过期 locator 永远不能接受或消费邀请码。
- 不会因重复提交创建两个成员或消费两次邀请码。
- 候选 Key 校验或登记失败时，成员创建和邀请码消费必须一并回滚。
- 原响应丢失后，即使成员随后被移出、退出、成为 Owner 或 Team 解散，操作查询仍返回原始加入结果和当前粗终态。
- 取消先提交时后到接受不能消费邀请；接受先提交时，普通成员执行补偿退出，已成为 Owner 时返回`accepted_owner`且不破坏唯一 Owner。
- 无副作用加入结果可在 locator 到期加 24 小时宽限后回收；只有签名 locator、操作 ID 和恢复秘密全部匹配，在 Team 线性化边界内确认 locator 已过期且不存在最小加入提交标记时，才能权威返回`expired_no_commit`，错误秘密仍返回统一错误。
- 成功加入必须与成员、Key、邀请消费一起原子写一条无秘密提交标记；完整结果 ACK 并清理、邀请摘要覆盖或 Team 解散后，该标记仍使历史查询返回`accepted`而非`expired_no_commit`。预览和取消不会创建标记。
- 远端不可达时可以停止自动重试，但不能删除待恢复记录；只有确定结果已持久化并 ACK，或取得经认证的`expired_no_commit`无副作用证明后才安全清除。

### SPEC-TEAM-005 — 成员终止

- Owner 可以移出普通成员，不能移出自己。
- 普通成员可以退出，Owner 不能直接退出。
- 移出或退出会撤销全部 Team 访问并停止容量承接新请求。
- 远端结果不确定时不会提前删除本机凭据。
- 退出凭据被撤销后，仍可用单用途恢复秘密查询该次操作结果。
- 退出响应或 ACK 丢失时可重复查询和 ACK；本机凭据删除失败不改变远端终态，展示清理待重试或只读清理说明。

### SPEC-TEAM-006 — 所有权转让

- 发起请求不会改变双方角色或撤销邀请码；请求只投影给当前 Owner 和指定目标。
- 只有指定目标可用当前有效凭据接受或拒绝，当前 Owner 只能撤销；请求 24 小时后按服务端时钟到期。
- 拒绝、撤销、到期、目标退出或被移出都不改变 Owner；五种终态与`accepted`互斥。
- 只有目标实时接受后才原子交换角色、撤销全部待用邀请码并让旧 Owner 失去管理权限。
- 接受与拒绝、撤销、到期或自动取消并发时，先获得 Team 线性化点者获胜。
- 接受与目标最后 Key 撤销并发时遵守 §12.4 和 §15.3，不产生零凭据的新 Owner。

### SPEC-TEAM-007 — 暂停与恢复

- 暂停阻止新请求、加入和邀请码生成，但允许管理和成员退出。
- 已准入请求允许排空。
- 恢复不会复活已过期、已撤销或已使用的邀请码。
- 暂停期间成员可以新增、更新或撤销自己的容量配置，但任何容量都不可路由；恢复后才按当前配置重新参与。
- 暂停 Team 的`active`容量不会进入新的定时 Provider 容量刷新；同一 Host 中仍运行的 Team 继续按原节奏刷新，用户主动容量操作不受此断言影响。暂停前已经发出的刷新可以完成，但其结果只能保留原`observedLifecycleRevision`并作为陈旧快照保存或丢弃，不得恢复当前可路由容量；排空后 Provider 自动读取次数保持不变。
- 暂停后不创建新的请求 Lease 或并发占用；暂停前已准入请求可完成并最终释放。恢复后的首次准入重新校验 Provider 容量，不使用暂停前缓存直接放行。
- 双 Host 验收覆盖`active r → paused r+1 → active r+2`：Host B 在 revision r 缓存或发起的 Provider 读取即使在恢复后才返回，也保持 revision r；Host A 或 B 的最终准入均在 Team 锁内拒绝该结果，锁外以 r+2 强制刷新并重新准入。旧结果不能创建 Lease、容量预留、使用事件或写成 r+2 的可路由缓存。
- 每次新的成功请求准入以服务端时钟原子写权威活动事件；`lastTeamRequestAt`只从这些事件单调汇总。页面浏览、认证、健康检查、后台刷新、拒绝准入和请求结算均不产生活动事件，且 Browser 不展示该摘要。并发请求不因更新 Team 生命周期行而互相串行，未来自动休眠在排他锁内复核权威事件。
- 无论空闲多久，本版都不会自动暂停或解散 Team；未来自动休眠只能进入可恢复的`paused`，自动解散不属于闲置策略。
- 重复暂停或恢复幂等且不重复审计；expected revision 不匹配时统一`409`，包括状态绕回原值后的 ABA 陈旧请求；陈旧恢复请求不能复活已解散 Team。

### SPEC-TEAM-008 — 解散

- 只有 Owner 可以解散 Team。
- 解散撤销所有邀请码、设备凭据、成员访问和容量贡献。
- 解散后拒绝新的用户业务请求及用户发起的 Team、成员、邀请、设备和容量写入。
- 清理失败可重试，不回滚 Team 终态。
- 响应丢失时可以确认同一操作的最终结果。
- 解散凭据被撤销后，仍可用单用途恢复秘密查询该次操作结果。
- 未认证加入 attempt 或普通可恢复操作配额耗尽时，已认证 Owner 的解散仍可使用 Team 专属终态槽提交和恢复，不能被持码者阻断。
- 终态查询、ACK、已准入结算、审计维护和后台清理仍可执行，但不能恢复 Team。
- 解散先提交后，晚到 OAuth 或容量回调不能重新激活贡献或保存可路由凭据；回调先提交时，解散必须将其一并终止。

### SPEC-TEAM-009 — 终态可解释

- 被移出、已退出、连接失效和 Team 已解散显示不同文案。
- Team 已解散不能误报为“已暂停”。
- 只读本地凭据来源提供明确的手动清理说明。
- 在 Key 撤销后的 365 天保证窗口内，旧 Key 必须分别得到`member_removed`、`member_left`、`team_dissolved`或`device_revoked`，完全未知 Key 才返回通用 `401`。

### SPEC-TEAM-010 — 安全边界

- Browser 不接收原始 Team Key 或 OAuth 凭据；邀请码明文只在生成结果、当前 Owner 显式再次查看结果和加入输入中短暂存在，不进入列表、URL、持久化存储、日志或遥测。再次查看必须使用显式非缓存动作并返回`Cache-Control: no-store`；关闭、切页、文档隐藏、检测到角色/连接变化或最长 60 秒窗口到期时清除明文，重开重新鉴权。
- Host same-origin 代理使用由监听配置确定的固定 Origin / Host allowlist 和 Host 签发的短时 CSRF/session capability；不能信任请求`Host`自证同源，受保护方法缺失`Origin`或 capability 必须在资源查找前同形拒绝。验收包含 DNS rebinding Host、伪造 Origin、缺失 Origin、缺失/错误/过期 capability，以及合法固定 loopback Origin；邀请码再次查看和全部写路由都必须通过同一边界。
- 日志和审计不包含秘密或请求内容。
- §17.2 的所有操作统一 Team-first 锁序；生成、接受、撤销邀请与暂停、转让、解散的双向并发结果符合矩阵且不会死锁。
- 并发撤销 Owner 设备凭据不会产生无人可管理但尚未解散的 Team。
- 错误恢复秘密、跨 Team/跨操作重放和同 operation ID 不同正文均不能执行变更；同 ID 不同绑定返回 `409`，查询错误不形成存在性探测。
- 未认证加入 attempt 与已认证操作使用隔离配额；持码者反复预览、取消或拒绝不能阻止成员退出或 Owner 解散。
- 退出、加入和解散在原响应、查询响应或 ACK 响应丢失时均可继续同一操作，不创建第二次副作用。

### SPEC-TEAM-011 — 升级迁移

- 零 Owner、多 Owner或无服务端有效 Owner 凭据的 Team 在任何迁移写入前被阻断并给出可操作报告；迁移不把服务端记录表述为明文持有证明。
- 旧 Admin 原子迁移为成员；其旧角色缓存和待用邀请码不能继续获得 Owner-only 能力。
- 非当前 Owner 创建或创建者不明的历史待用邀请码被原子撤销并覆盖摘要。
- 旧显示名称的非法值和规范化冲突按 §21.2 确定性修复，随后数据库部分唯一约束可成功建立。
- Browser 原始 Key `connect`和不安全的本地单删入口不可再用，已有 Host 凭据仍只停留在 Host 层。
- 有权威历史准入事件的 Team 以其最大服务端时间回填`lastTeamRequestAt`；历史不完整时保持为空且未来启用自动休眠时获得完整新宽限期，不得因空值立即暂停旧 Team。

### SPEC-TEAM-012 — 用量与个人账号共享边界

- Browser 一级导航只使用`用量`、`成员`和 Owner 专属的`邀请码`；不再显示“个人”导航组，也不在 Team 工作区重复展示个人账号共享模块。个人共享沿用现有 Codex 账号管理入口；用量页不得重新使用含义混杂的`容量`命名。
- 用量只展示跨成员共享 attempt 的`预估费用（USD）`、`Token 用量`、`请求次数`、紧凑数据状态和明确时间窗口；self-use 不计入，`我的用量`严格按当前`consumerMemberId`裁剪，Team Owner 的`Team 总用量`包含自己的子集而非另一个可相加集合。
- Token 规则、USD 预估规则和版本化价格合同与 §16.2 一致；缓存输入大于输入、负数、超上限、非整数或缺失字段不能结算 Token 或费用，模型/档位无法可靠定价时只能结算 Token。Credits 只留在 Host 内部，不进入 Browser。
- `requestCount = 0`显示可靠`US$ 0.00 / 0 Token / 0 次请求`；请求不为零而相应覆盖为零时显示`—`；部分覆盖时只显示已有小计并标为`部分数据`，完整数据必须同时满足 Token 和费用覆盖。完整数据是默认正常态，不额外显示状态标签；只有部分、未计量、零请求或获取失败等需要用户理解的状态才明确展示。
- 默认界面不放置“这些数字是什么”式解释模块，不展示 Credits、输入/缓存/输出 Token 拆分、实际账单、余额或虚构的剩余容量进度条；语义通过指标名`预估费用（USD）`和简短状态表达。
- Team Owner 只获得 Team 汇总和自己的汇总，普通成员只获得自己的汇总；服务端投影而非 Browser 过滤负责阻止其他成员明细泄漏。
- 任何 Browser usage 响应都不包含逐条事件、成员/账号/模型字段；任何 Browser contributions 响应都只含当前成员自己的来源。Owner/成员直接调用 API 的验收必须证明这些限制，不以入口隐藏代替授权。
- 暂停期间用量仍可读取，暂停前已准入请求的晚结算可更新其`admittedAt / startedAt`原窗口汇总但不得改归结算日；没有可靠数据时显示不可用状态。
- Codex 账号管理区只投影并修改当前成员自己的来源和状态；Owner 与成员规则相同，暂停期间可编辑但不可路由。Team 设置不重复渲染个人共享入口。
- 用量、成员和邀请码是三个顶层任务；个人身份在 Team 头部表达，成员关系与 Team 级操作按角色收口到 Team 管理菜单。界面仍不得回到单个长弹窗或混合危险区。
- 320px 和 375px 宽度下不得产生页面级横向滚动；Team 标题、状态和主操作按顺序堆叠，金额、Token 与请求次数不得被截断，主要触控目标不小于 44px。弹窗只允许内容区内部滚动，打开时锁定背景滚动。
- 768px 宽度下必须先呈现 Team 上下文，再呈现三个顶层工作区入口；全部入口可达，导航、内容和原型场景控制不得互相覆盖。原型专用控制不属于正式产品信息架构。

## 23. 本版已锁定的产品决策

本规格 v0.2 采用以下明确决策：

1. 角色只有 Team Owner 和成员，不保留 Admin。
2. 每个有效 Team 恰好一位 Owner。
3. 普通成员看不到邀请码管理及其元数据。
4. 邀请码仍是只能成功加入一次的 Bearer 凭据；当前 Owner 可以对`revealable = true`且仍有效的新邀请码显式再次查看和复制完整值，但普通列表保持无秘密，关闭查看界面后 Browser 立即清除明文。升级前只保存摘要的旧有效码仍可用于加入但`revealable = false`，只能撤销后重新生成，不能伪造恢复。
5. 有效成员显示名称按固定 Unicode 规则在 Team 内唯一，但名称不代表经过验证的身份。
6. 所有权转让采用当前 Owner 发起、指定目标成员实时接受的两阶段流程；发起本身不改变角色。
7. 所有权转让完成时撤销 Team 中全部尚未使用的邀请码，发起或拒绝不会撤销。
8. Team 暂停期间不能生成或使用邀请码；可预览，成员仍可通过 Codex 账号管理区编辑自己的共享配置，但对应技术容量不可路由。
9. Owner 不能直接退出，只能先转让或解散。
10. 解散不可恢复，采用逻辑终态并保留必要审计和终态诊断。
11. 加入、退出和解散都使用可恢复的操作协议；通常必须 ACK，只有签名 locator 可认证证明从未提交副作用的加入操作可以无服务端 ACK 清理。结果不确定时不能靠删除本机状态“放弃”。
12. 断开设备不是普通成员生命周期主路径，在设备恢复闭环完成前降为高级能力。
13. 成员列表不显示头像、邮箱、在线状态或虚构的活动信息。
14. 一级导航只保留用量、成员和 Owner 专属邀请码；个人账号共享沿用现有 Codex 账号管理入口，不在 Team 设置中重复展示；Team 身份在头部展示，退出、转让和解散按角色收口到 Team 管理菜单；`容量`只保留为后端技术概念。
15. 升级时旧 Admin 变为成员，非当前 Owner 创建的待用邀请码失效，旧权限不能经缓存或旧接口继续使用。
16. 生命周期写入使用单调`lifecycleRevision`和 expected revision，状态绕回相同值也不能让陈旧请求生效。
17. 每份邀请码只有一个短时加入 attempt 槽；无副作用结果可安全回收，真实成功加入保留最小提交标记，且加入配额与成员退出、Owner 解散隔离。
18. 服务端保证有效 Owner 凭据不变量和当前请求的持有证明，但不虚构对用户本机明文是否仍存在的认知。
19. 本版只有 Owner 手动暂停；暂停是保留身份、配置和凭据的低资源休眠，后台容量监控不得继续主动读取该 Team 的 Provider。
20. 服务端记录不面向 Browser 的`lastTeamRequestAt`作为未来闲置策略依据，但本版不按时间自动改变状态；长期闲置永不自动解散 Team。
21. 本版消费展示使用预估费用（USD）、Token 用量、请求次数和紧凑数据状态；Credits 只留在 Host 内部，Browser 不展示 Token 拆分、实际账单、余额或虚构的剩余容量。
